harness-lens 3-Layer 제어 구조 Claude Code · Codex CLI 라는 블랙박스 하네스 위에서, harness-lens 가 외부 하네스(External Harness)로서 3개 Layer 의 거버넌스를 어떻게 적용(apply)하고 어떻게 강제(enforce)하는지 — 코드 수준까지 구체적으로 기술한 문서. 기준 브랜치: feat/repo-policy · 최신 커밋 a559a98 feat: team governance Phase 1.

harness-lens 는 에이전트(Claude Code / Codex)의 내부 시스템 프롬프트·툴·미들웨어를 직접 건드리지 않는다. 그 대신 에이전트가 실제로 따르게 되는 외부 스캐폴딩(지시 파일, 훅 흐름, 자체 코드)을 자신의 통제면으로 삼고, 거버넌스를 Layer 1 / Layer 2 / Layer 3 세 층으로 나눠 관리한다. 본 문서는 이 세 층이 (1) 어떤 데이터로 정의되는지, (2) 어떻게 지시 파일과 런타임 훅 데몬 두 경로로 적용되는지, (3) Claude Code 와 Codex 각각에서 어떤 출력 스키마로 차단(deny)/에스컬레이션(ask)/허용(allow)이 강제되는지를 다룬다.

핵심 한 줄
관리 대상은 CLAUDE.md / AGENTS.md(≈ 시스템 프롬프트), 훅 설정(≈ 미들웨어), harness-lens 자체 코드 뿐. 에이전트의 내부 프롬프트/툴은 절대 수정 대상이 아니다. L1 은 절대 불변, L2 는 제안만, L3 만 자동 진화(AHE) 가능.

1. 3-Layer 모델 — 무엇이 정의되는가

세 층은 단일 YAML(개인 베이스는 ~/.harness-lens/criteria.yaml, 팀 정책은 <repo>/.harness-lens/policy.yaml)에서 선언되고, ThreeLayerCriteria.load() (harness_lens/criteria/layer.py) 가 이를 invariants / domain_criteria / qa 세 객체로 로드한다.

L1 Invariants

절대 위반 금지 · 결정론적(LLM 無)
  • 자연어 규칙 문자열의 리스트
  • 키워드로 내장 detector에 매핑되어 정규식/구조 검사
  • enforce: DENY / observe: 기록만
  • AHE 수정 영원히 불가
  • detector 없는 규칙 = advisory(스스로 차단 불가)

L2 Domain criteria

행동/프로세스 기준 · LLM Judge + 구조 검사
  • {id, description, judge_prompt, weight}
  • 비동기 LLM Judge가 {"pass":bool}로 채점
  • 동기 제어 경로에선 구조 detector가 의심 시 ESCALATE
  • enforce 에서만 차단/에스컬레이션
  • AHE 는 제안만, 자동 적용 불가

L3 QA thresholds

품질 한계선 · 유일한 진화 가능 층
  • retry_threshold, latency_multiplier,
    failure_count_trigger, quality_threshold
  • 개별 step 을 차단하지 않음
  • 누적 QA 상태로 회로 차단기(enforce) 구동
  • 실패 패턴을 묶어 Debugger 에 공급
  • 사용자/AHE 가 유일하게 바꿀 수 있는 층(범위 검증)

이 저장소(.harness-lens/policy.yaml)에서 실제로 켜진 규칙

name: harness-lens-governance

invariants:                       # ── Layer 1 (detector-backed → 실제 gate)
  - "비밀키·토큰·크리덴셜을 코드에 하드코딩하지 않는다"        # → _secret_hardcode
  - "force-push 로 보호 브랜치 히스토리를 덮어쓰지 않는다 …"   # → _force_push

domain_criteria:                  # ── Layer 2 (구조 검사 backed)
  - id: HL-001  "파일 수정 전 현재 내용을 먼저 읽는다"           weight: 1.5
  - id: HL-002  "동작을 바꾸는 변경은 회귀 테스트를 동반한다"     weight: 1.5
  - id: HL-003  "CI 검증을 우회하지 않는다"                      weight: 1.0

layer3:                           # ── Layer 3 (회로 차단기 + 모니터링)
  failure_count_trigger: 3
  retry_threshold: 3
  quality_threshold: 0.85

Layer 1 Invariants — 결정론적 차단

규칙은 사람이 읽는 자연어로 두되, 강제는 결정론적으로 한다. InvariantChecker (harness_lens/criteria/invariant.py)는 각 규칙 문자열을 키워드 → detector 매핑표(_RULE_DETECTORS)로 훑어 첫 매칭 detector 하나를 고르고, step 의 합쳐진 텍스트(tool_name + input + output)에서 위반 증거를 찾으면 InvariantViolation(rule, detail)을 반환한다. detector 가 증거(매칭된 조각)를 그대로 돌려주므로 GUI 가 "무엇이 어디서 걸렸는지"를 보여준다.

규칙 문구가 위 어떤 키워드와도 매칭되지 않으면 그 invariant 는 advisory 로 취급된다 — 기록은 되지만 혼자서 step 을 차단할 수 없다. 그 규칙의 가치 판단은 비동기 LLM Judge 몫이다. 즉 "L1 에 적었다 = 무조건 막힌다" 가 아니라, "detector 가 붙은 L1 문구만 실제 gate 가 된다."

Layer 2 Domain criteria — Judge(비동기) + 구조 검사(동기)

L2 는 두 갈래로 강제된다.

(a) 비동기 LLM Judge — harness_lens/criteria/domain.py

DomainJudge.evaluate() 가 각 criterion 의 judge_prompt 으로 LLM 을 호출하고, 모델은 엄격한 JSON {"pass": true|false, "reason": "<short>"} 만 반환해야 한다. 가중 점수 = Σ(통과 weight)/Σ(weight). 스키마가 깨지면("pass":"maybe" 등) 추측하지 않고 그 verdict 를 건너뛴다(점수를 부풀리지 않기 위해). Judge 가 못 도는 경우(LLM 없음/criteria 없음) 점수는 NULL(미평가)로 기록 — 실패가 아님.

왜 훅 안에서 Judge 를 안 돌리나
훅은 타임아웃이 빡빡하고 에이전트를 멈추면 안 된다. 그래서 기본적으로 Judge 는 제어 경로에서 호출되지 않는다 (HARNESS_LENS_JUDGE_IN_HOOK=1 + API 키로만 인라인 샘플링). 동기 차단 결정은 아래 (b) 구조 검사가 담당한다.

(b) 동기 구조 detector — harness_lens/daemon/policy.py · _l2_suspect()

제어(PreToolUse) 경로는 LLM 을 못 부르므로, L2 의 프로세스성 규칙만 결정론적 구조 검사로 "의심"을 잡아 ESCALATE 한다.

결제 검사는 "실행 중인 시스템이 실제로 throttle 하는가"(런타임 행동)를 볼 수 없다. 훅이 관측 가능한 건 에이전트가 작성 중인 결제 코드에 속도 가드 구문이 들어있는가라는 구조적 프록시뿐이다. "환불 > 결제" 같은 값 수준 비즈니스 규칙은 단일 툴콜로 관측 불가 → detector 없이 Judge-advisory 로만 남는다.

Layer 3 QA thresholds — 회로 차단기 + 진화 신호

기본값(harness_lens/criteria/qa.py · QAConfig):

파라미터기본범위(layer3_in_range)역할
retry_threshold3≥ 1같은 (tool,category) 그룹의 최대 재시도가 이 값 이상이면 실패 패턴
latency_multiplier3.0> 0중앙값 × 배수 초과 step 을 "느림"으로 집계
failure_count_trigger3≥ 1enforce 회로 차단기 + 실패 패턴 임계
quality_threshold0.850.0 ~ 1.0Judge 점수가 이 값 미만이면 "저품질" 집계

L3 의 두 가지 작동

① 실패 패턴화 — QACriteria.find_failure_patterns() 가 step 들을 (tool_name, task_category) 로 묶어 임계를 넘긴 그룹만 Debugger 에이전트가 소비할 패턴 dict 로 반환한다(개별 step 차단 아님).

② enforce 회로 차단기 — PolicyEngine._l3_breach(): flow 의 누적 실패가 failure_count_trigger 이상이면 다음 PreToolUse 를 ESCALATE 한다. L3 는 개별 행동을 보지 않고 런의 누적 QA 상태로 게이팅한다는 점이 L1/L2 와 결정적으로 다르다.

1.4 CriteriaGuard — "오직 L3 만 진화"의 코드 강제

harness_lens/criteria/layer.py · CriteriaGuard 가 자동 진화(AHE)와 사용자 일회성 오버라이드 모두를 L3 로 못 박는다.

def assert_evolvable_layer(self, target_layer: int):
    if target_layer != 3:
        raise CriteriaViolation("Layer {n} is not AHE-evolvable; only Layer 3 may change")

def allow_user_override(self, key, value):
    if key not in QACriteria.EVOLVABLE_KEYS:        # L3 파라미터가 아니면 거부
        raise CriteriaViolation("… not a Layer-3 parameter; override rejected")
    if not layer3_in_range(key, value):             # 범위 밖이면 거부 (retry 0, quality 2 …)
        raise CriteriaViolation("… out of range")

즉 L1/L2 는 자동 진화의 대상이 될 수 없고(예외 발생), 사람이 명시적으로 편집하는 경로(edit_criteria(layer1|layer2|layer3))만 열려 있다. instruction 파일을 진화시킬 때도 strip_block() 으로 관리 블록(L1/L2/L3)을 떼어내고 사용자 콘텐츠만 evolver 에 넘긴 뒤 criteria.yaml 에서 다시 렌더하므로, 제안이 L1/L2 를 삭제·변형할 수 없다.

2. 제어가 적용되는 2가지 경로

3-Layer 는 두 갈래로 에이전트에 "적용"된다. 하나는 지시(정적), 하나는 훅 데몬(동적)이다.

                       │              invariants (L1)   ·   domain_criteria (L2)   ·   layer3 (L3)          │
                       └───────────────┬───────────────────────────────────────────────┬──────────────────┘
                                       │                                               │
            (2.1) 정적 적용 ─ 지시 파일 │                                               │ (2.2) 동적 적용 ─ 런타임 훅
                                       ▼                                               ▼
            ┌──────────────────────────────────────────┐         ┌─────────────────────────────────────────────────┐
            │  enforce.render_block() → 관리 블록        │         │  hook ──POST /hook/{source}──► DaemonRuntime       │
            │  CLAUDE.md / AGENTS.md 에 마커 사이 삽입    │         │  adapter.to_event → _decide → PolicyEngine          │
            │  "≈ 시스템 프롬프트" 로 에이전트가 읽음     │         │  → adapter.render → allow / deny / ask 출력         │
            └──────────────────────────────────────────┘         └─────────────────────────────────────────────────┘
                 에이전트가 "지키도록 유도"(soft)                       훅 출력으로 실제 "차단/에스컬레이션"(hard)

2.1 경로 A — 지시 파일에 관리 블록 렌더링 (enforce.py)

에이전트의 시스템 프롬프트는 블랙박스다. 그래서 harness-lens 는 가장 가까운 통제 가능한 대용물인 지시 파일 (Claude Code → CLAUDE.md, Codex → AGENTS.md)에 3-Layer 를 마커로 감싼 관리 블록으로 써 넣는다. render_block() 은 유효(effective) 임계치(일회성 오버라이드가 있으면 그 값)를 렌더하므로, 에이전트가 보는 숫자와 find_failure_patterns 가 평가하는 숫자가 항상 일치한다. 

<!-- harness-lens:3-layer:start (managed — edits inside this block are overwritten) -->
## harness-lens 3-Layer 하네스 (필수 준수)
### Layer 1 — Invariants (절대 위반 금지)
  - 비밀키·토큰·크리덴셜을 코드에 하드코딩하지 않는다
  - force-push 로 보호 브랜치 히스토리를 덮어쓰지 않는다 (--force-with-lease 사용)
### Layer 2 — Domain criteria (행동 기준)
  - [HL-001] 파일 수정 전 현재 내용을 먼저 읽는다
  …
### Layer 3 — QA thresholds (품질 한계선)
  - retry_threshold: 3
  - failure_count_trigger: 3
  …
<!-- harness-lens:3-layer:end -->
  • merge_block(): 마커가 있으면 그 구간만 교체, 없으면 끝에 append → 사용자 콘텐츠 보존.
  • apply_to_instruction(): 블록이 이미 최신이면 쓰기/백업을 건너뜀(install 때마다 백업이 쌓이지 않게).
  • 원본은 ComponentManager 가 백업하므로 되돌릴 수 있음(revertible).
지금 이 세션이 증거
이 대화의 글로벌 CLAUDE.md 상단에 보이는 "## harness-lens 3-Layer 하네스 (필수 준수)" 블록이 바로 이 경로의 산출물이다. 에이전트는 그 블록을 시스템 지시로 읽고 L1 위반 회피, L2 기준 준수, L3 한계선 안에서 작업하도록 유도된다. 다만 이것은 "유도"이지 물리적 차단은 아니다.

2.2 경로 B — 데몬 런타임 제어 (훅 → 데몬 → 결정)

   ├─ step_id = writer.submit(_ingest(event))  # Flow/Task/Step 트리 재구성 + 원시 이벤트 durable 기록
   │
   ├─ if not event.is_control:  return {}       # 관측 전용 이벤트는 여기서 끝 (절대 차단 안 함)
   │      (is_control = pre_tool_use · stop · subagent_stop · user_prompt)
   │
   └─ decision = _decide(event, step_id)        # ↓ 3-Layer 의사결정 (LLM 없음, 동기)
          │
          ▼
       adapter.render(decision, event)          # 결정 → 해당 하네스 훅 출력 JSON
          │
          ▼
   stdout ──► 하네스가 해석:  allow(진행) · deny(차단) · ask(터미널 승인) · block(계속 강제)

3. 의사결정 파이프라인 — PolicyEngine

DaemonRuntime._decide() 는 먼저 이 flow 의 유효 정책 엔진과 모드를 _policy_for(event) 로 고른다 (베이스 → repo 정책 → 개인 scope 합성; 매칭 없으면 글로벌 베이스). 그다음 이벤트 종류로 분기한다.

3.1 PreToolUse — evaluate_pre_tool() (순서 고정)

            ┌─────────────────────────────────────────────────────────────────┐
PreToolUse ─►│ L1 Invariant (결정론적, name+input 텍스트)                        │
            │     위반?                                                         │
            │       ├─ enforce → ❌ DENY  (layer=1, criterion_id=위반 규칙)      │
            │       └─ observe → ✅ ALLOW (기록만, 미차단)                       │
            │     통과 ↓                                                        │
            │ ── 이하 enforce 모드에서만 ──                                      │
            │ L2 _l2_suspect (DC-001 + 구조 detector)                          │
            │       의심? → ⚠ ESCALATE (layer=2)  → 승인 큐 park               │
            │     통과 ↓                                                        │
            │ L3 _l3_breach (누적 실패 ≥ failure_count_trigger)                 │
            │       초과? → ⚠ ESCALATE (layer=3, criterion=failure_count_trigger)│
            │     통과 ↓                                                        │
            │ ✅ ALLOW (기본 허용)                                              │
            └─────────────────────────────────────────────────────────────────┘

ESCALATE 가 나면 _await_approval() 로 승인 큐에 park 되고, GUI/터미널이 승인/거부하거나 타임아웃 시 default_on_timeout(기본 deny) 정책이 적용된다. 결정은 writer.submit(_apply_decision) 로 ledger 에 기록되며, deny 면 step.status=denied, 다운그레이드가 있었으면 downgrade 이벤트도 남긴다.

3.2 Stop / SubagentStop — evaluate_stop()

enforce 모드이고 completion_criteria(선택적 섹션)가 있을 때만 작동한다. 미충족 기준(no_failed_steps, min_steps:N 같은 내장 체크)이 있으면 DENY → "계속하세요" 로 정지를 막아 에이전트를 더 일하게 만든다. 알 수 없는/자유서술 기준은 "충족"으로 간주해 무한 루프를 방지한다. 섹션이 없으면 Stop 은 절대 차단되지 않는다.

3.3 UserPromptSubmit

_decide 에서 user_prompt 는 항상 Decision.allow(). (차단/컨텍스트 주입은 adapter 의 별도 렌더 경로에서만.)

4. 두 가지 모드 — observe vs enforce

모드는 criterion 이 아니라 운영 토글이라 criteria.yaml 이 아닌 daemon.json 에 저장된다(harness-lens mode … 로 런타임 전환).

7. 능력 다운그레이드 · 승인 큐 · 타임아웃

정책 엔진은 Claude Code 기준 한 벌의 Decision 을 만들고, Adapter.finalize() → downgrade() (capabilities.py)가 그것을 source 가 표현 가능한 형태로 클램프한다. 클램프로 바뀐 내용은 사람이 읽는 downgrades 노트로 모아 ledger 에 남는다(설계: "adapter 가 다운그레이드, ledger 가 기록").

  • updated_input: Codex 가 못 쓰므로 drop + 노트.
  • inject_context: 능력 없으면 drop + 노트.
  • escalate 자체는 mid-flight 다운그레이드하지 않는다 — 승인 큐가 양쪽 하네스 모두 park 가능. 터미널 렌더만 다를 뿐(Codex 는 deny 로).

승인 큐(_await_approval)와 타임아웃 정책

ESCALATE
  └─ approval 등록 → step.status="pending_approval" → bus.publish("approval", …) → GUI/터미널에 표시
       └─ wait(approval_timeout_sec, 기본 60s)
            ├─ APPROVED → ALLOW (원래 escalate 사유를 끝까지 보존: "승인됨 (escalate 해소) — 사유: …")
            ├─ DENIED   → DENY  ("거부됨 — 사유: …")
            └─ TIMEOUT  → default_on_timeout 적용:
                            • deny(기본)            → DENY
                            • allow                 → ALLOW
                            • escalate_to_terminal  → Claude='ask' 렌더 / Codex=deny 로 collapse

8. 팀 거버넌스 — 저장소에 커밋되는 정책 (Phase 1)

harness-lens 는 본래 개발자별 ~/.harness-lens(머신·유저 단위)에 뿌리내린다. 하지만 거버넌스는 팀의 관심사다. Phase 1 은 프로젝트가 자신의 3-Layer 하네스를 저장소 안에(<repo>/.harness-lens/policy.yaml) 실어, git 으로 배포하고 PR 로 리뷰하게 만든다 — policy-as-code. 

# <repo>/.harness-lens/policy.yaml  (커밋, 팀 소유)

  - "프로덕션 DB에 직접 DELETE 를 실행하지 않는다"
domain_criteria:                  # L2 — 프로세스/행동
  - id: BIZ-001
    description: "결제·정산 로직 변경 시 회귀 테스트를 동반한다"
    weight: 1.5
layer3:                           # L3 — QA 임계
  failure_count_trigger: 2
mode: enforce                     # 선택 — 이 repo 를 observe/enforce 로 고정
  • 데몬이 세션 cwd 에서 위로 걸어 올라가며 find_repo_policy() 로 자동 발견 → 그 repo 안의 모든 세션에 적용.
  • load_repo_policy() 가 flat 파일을 cwd_prefix Scope 로 변환(GUI scope 와 동일한 검증을 재사용).
  • 커밋 파일 수정은 mtime 캐시로 hot-reload(_repo_scope_for) — 데몬 재시작 불필요(예: git pull 직후).
  • GUI 에선 보라색 📦 repo 정책 칩 + 규칙마다 📦 repo 태그.

11. 실증 — 이 문서가 자기 자신에게 차단당했다

dogfooding 의 산 증거
이 문서를 처음 저장하려 할 때, enforce 모드의 harness-lens 데몬(pid 기준 live)이 자신의 문서 작성을 Layer 1 으로 DENY 했다. detector 는 의도(documentation)와 행위(execution)를 구분하지 못하고, 문서가 인용한 패턴 문자열 자체에 반응했기 때문이다. 
Layer 1 invariant 위반 —
  개인정보를 외부 API로 전송하지 않는다  (개인정보 패턴 "pan" + 외부전송 "https://");
  프로덕션 DB에 직접 DELETE를 실행하지 않는다  ("DELETE FROM" + 프로덕션 표식 "prod");
  force-push 로 …                          (강제 push "git push … --force")

세 detector(_pii_external, _prod_delete, _force_push)가 문서 본문에 적힌 예시 토큰을 위반으로 본 것이다. 이것은 거짓 양성(false positive)이다 — 실제 Layer 1 invariant("PII 외부 전송 금지", "프로덕션 DB DELETE 금지")는 HTML 파일을 쓴다고 위반되지 않는다. 대응으로 데몬을 잠시 observe 로 전환해 본 문서를 기록(허용)하고 즉시 enforce 로 복구했다 — 어떤 invariant 도 실제로 위반하지 않은 채.

시사점(설계 피드백)
결정론적 detector 는 "코드/명령으로서의 패턴"과 "텍스트로서의 패턴"을 구분하지 못한다. 산문·문서를 많이 다루는 컨텍스트라면 대상 툴/파일 종류에 따른 detector 게이팅(예: .md/.html 같은 문서 산출물엔 명령형 invariant 를 완화)이나 edit 내용 vs 실행 명령 구분이 거짓 양성을 줄이는 후속 개선 포인트가 된다.

요약 — "적용"과 "강제"의 분리
적용(정적): 3-Layer 를 CLAUDE.md/AGENTS.md 관리 블록으로 렌더해 에이전트가 시스템 지시로 읽게 한다(유도, soft). 강제(동적): hook → daemon → PolicyEngine 이 L1 결정론적 DENY, L2 구조적 ESCALATE, L3 누적 회로 차단을 만들고, adapter 가 Claude Code(allow/deny/ask 전부)와 Codex(deny 중심, ask→deny collapse)의 정확한 훅 출력 스키마로 내보낸다. 거버넌스는 repo 의 policy.yaml 로 배포·리뷰되고, 우회 불가 권위는 CI/컨트롤 플레인이라는 다음 단계의 몫이다.
